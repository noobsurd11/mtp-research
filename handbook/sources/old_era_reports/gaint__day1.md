## 3. Checkpoint resume, watchdog, ALHVR relaunch

### What was built
* **`checkpoints/latest.pth`** every `training.checkpoint_every` = 2000 steps and at the last step, written atomically (tmp + rename).
  It holds every model (A/B for ALHVR, student + EMA teacher for MT), every optimizer and scheduler, the grad scaler,
  the python, numpy, torch-CPU and all CUDA RNG states, the step, the val history, the train curve, the best-val record and a CPU copy of the
  best weights. `best.pth` is unchanged. These are the only two checkpoint files, and both are git-ignored.
* **`scripts/train.py --resume`** continues from `latest.pth`. The config must equal the stored one (hard error otherwise).
  If the interrupted run overwrote `best.pth` after its last `latest.pth`, the best weights as of that step are put back.
  `regions.csv` is trimmed back to the resume step. `train.log` is appended. A run directory that already has outputs needs
  `--resume` or `--overwrite`, so nothing is clobbered silently.
* **Deterministic data stream** (`src/data/stream.py`). The batch at step *s* is a pure function of (seed, *s*): per-epoch
  permutations come from seeded generators, and every sample carries its own augmentation seed. Resuming therefore needs no
  data-loader state, and the stream does not depend on the number of workers.
* **`metrics.json`** now records `total_steps`, `optimizer_steps`, `resumes` (step and time of every resume), `amp_dtype` and `deterministic`.
* **bf16 autocast** everywhere (`training.amp_dtype: bfloat16`). The grad scaler is active only for fp16, but it is checkpointed either way.
* **`scripts/launch.py` / `src/utils/jobs.py`**: memory guard, job limit and watchdog.
  * Before each launch it runs `torch.cuda.mem_get_info` in a subprocess and requires free ≥ expected peak + 2 GiB, with at
    most 2 of our training processes at a time. Otherwise the job queues.
  * Launches are serialised by a file lock. Each one waits for the new run's first logged step, so the next check sees its memory.
  * Waiting jobs are served first come, first served among the jobs that fit.
  * Watchdog: if the run dies it waits for a slot and relaunches **once**, with `--resume` if `latest.pth` exists
    and with `--overwrite` otherwise. SIGTERM to the launcher is forwarded to the run and never triggers a restart.
  * Every decision is logged to `experiments/<run>/launch.log`.

### Problems found on the way (these affect comparability with the pilots)
1. **The pilots trained with correlated augmentations (pre-existing bug).** `seed_worker` called
   `Compose.set_random_seed(seed)` in every DataLoader worker. That gives *every* transform the same seed, so each transform draws
   its apply/skip coin from an identical generator:
   * HorizontalFlip and VerticalFlip always fired together, so single flips never happened;
   * RandomRotate90 and Rotate were partly coupled to the flips;
   * GaussianBlur (p 0.3) and GaussNoise (p 0.3) always fired together, and with them brightness/contrast (p 0.4).

   Measured: with seeded flips over 1000 draws, only 2 of the 4 flip combinations occur. All pilots used `num_workers=4`, so
   **every pilot run (SL, MT, ALHVR) trained with this coupled augmentation**. The new stream gives each transform an
   independent seed (regression check: all 4 flip combinations, about 25 % each). **The relaunched ALHVR and all new runs
   therefore do not use exactly the pilots' augmentation.** Decision: the pilot baselines are rerun on the current code
   (`sl_20pct_s0`, `sl_100pct_s0`, `mt_20pct_s0`, night Lane A after ALHVR). Pilot numbers are reported only in their own
   "pilot, coupled-augmentation code" table, never mixed with current-code numbers.
2. **`torch.use_deterministic_algorithms(True)` makes U-Net++ 5.3× slower** (1.57 vs 8.35 it/s at 512 px, batch 4). Training
   runs therefore keep the pilots' setting (cuDNN deterministic, benchmark off). They are close to reproducible but not
   bitwise, because the bilinear-upsampling backward uses atomics. `deterministic: strict` turns full determinism on, and
   the resume test uses it.
3. **Weighted CE on CUDA was not deterministic.** `nll_loss2d` with class weights reduces with atomics. `WeightedCrossEntropyLoss`
   now computes the per-pixel loss and the weighted mean itself. It is the same formula (difference 7e-7 vs PyTorch) and is
   deterministic.
4. The CE implementation (3) and the bf16 autocast (global rule) are further small differences from the pilot code.

## 6. Metrics module: standard / pvs3 / pratt_median

`src/evaluation/metrics.py` is the only metrics implementation. It is used by validation and test in the trainer, by
`scripts/evaluate.py`, by `scripts/probes.py` and by the results table. One pass builds a per-image confusion matrix
(a single `bincount`), and every convention is derived from it. Ignore-label pixels never enter any count
(BenchmarkEL 255, UCF-EL 128).

* **standard:** a global confusion matrix over all pixels. Per class it gives IoU, P, R and F1 = 2TP/(2TP+FP+FN), the defect-only mean and the
  all-class mean. A class absent from the ground truth is NaN and excluded from the means. A class that is present but never predicted has precision
  NaN (0/0) and IoU = F1 = 0.
* **pvs3:** the same, after dropping every pixel whose ground truth is background (the background row of the
  confusion matrix is zeroed). Background is then absent.
* **pratt_median:** per-image IoU per class, then the median over images, averaged over crack, gridline and inactive (BenchmarkEL; on UCF it uses the 4
  defect classes). Images where the class is absent from the ground truth are handled by three rules: **A** exclude the image, **B** score 0 (primary),
  **C** score 1 if the class is also not predicted there, else 0.
* The pre-existing top-level keys (`defect_miou`, `crack_recall_relaxed`, `crack_fpr_image`, …) are unchanged, and so are their 14 old tests.
* **Tests** (`tests/test_metric_conventions.py`, 14 pass):
  * on random cases, recall per class is identical under standard and pvs3 (and pvs3 precision ≥ standard);
  * IoU = F1/(2−F1) per class under both conventions;
  * hand-computed toy cases for rules A, B and C (A 2/3, B 1/6, C 2/3), plus the mean over classes and the ignore label;
  * an all-crack predictor on a 10 bg / 4 crack / 2 other toy mask gives:
    * standard: crack IoU 4/16, P 4/16, R 1, F1 0.4;
    * pvs3: crack IoU 4/6, P 4/6, R 1, F1 0.8, background absent, and the defect-mean recall is unchanged.

## 8. PV-S3 trainer (reimplementation of Jha et al.)

`method: pvs3` runs on the Mean Teacher path of the shared trainer, so it gets the same checkpointing and resume. There are two recipes:
**v1** (`configs/ucf_pvs3.yaml`, run `ucf_pvs3_ssl20_s0`) is a **failed recipe** (see "Latest status" and below), and **v2**
(`configs/ucf_pvs3_v2.yaml`, since 22:25 on Sat) is the current one. The description below is v1 unless marked v2.

* EMA decay 0.99 (weights and BN buffers). The teacher has `requires_grad=False` and is updated only by EMA.
* The geometry is drawn **once** per sample (shorter side 295, random 256 crop, h/v flips) and shared by both views:
  * teacher: weak view (normalise only);
  * student: strong view (colour jitter ±50 %, random grey p 0.2, Gaussian blur k 1–5 / σ 0.1–2.0), **photometric only**.
    **CutMix (in Jha's strong augmentation) is left out** because it is not photometric.
* Labelled images:
  * **v1:** CE on the student's strong view (jitter and blur on every image). **This was a deviation from standard Mean Teacher
    practice, and the likely cause of v1's failure.**
  * **v2:** CE on the **weak** view, i.e. exactly the augmentation of the SL arms (shorter side 295, random 256 crop, h/v flips).
* Unlabelled images: SemiCE = CE towards the teacher's argmax where the teacher's max softmax ≥ t_pos = 0.6; t_neg = 0 switches the negative term
  off (any other value raises).
* Strong view, in both versions applied only on top of the shared geometry and photometric only:
  * **v1:** jitter p 1.0, grey p 0.2, blur p 1.0.
  * **v2:** jitter p 0.8 (±50 %), grey p 0.2, blur p 0.5, and used **only for the student on unlabelled images**.
* **Labelled-view rule:** the labelled loss sees the augmentation of the matching SL arm. On UCF that is the weak view (v2); on BenchmarkEL's Mean Teacher it is
  the "strong" view, because BenchmarkEL's SL arms train with those photometric ops (`configs/ssl_mean_teacher.yaml: labeled_view: strong`).
* **Not reproduced:** the earlier PV-S3 implementation (your records: **46.4 standard**) is not reproduced by v1 (0.200) or v2 (0.276, 0.283). The old
  code is lost, and the cause is open.
* **Pseudo-label logging** (every PV-S3 run from 2026-10-04 08:55): per-class counts of confident pseudo-label pixels, summed over each 500-step window,
  go to `experiments/<run>/pseudo_labels.csv` and the log. This is logging only, and it is trimmed back on resume. Tested in `tests/test_pvs3.py`.
* **Per-class thresholds (`configs/ucf_pvs3_v2_classthr.yaml`, `src/losses/class_threshold_ce.py`, added Sun 12:15):**
  * Thresholds start at t_pos 0.6.
  * Every 500 steps, a histogram of (teacher argmax, confidence) over that window gives each class the lowest threshold ≥ 0.6 (on a 0.001 grid) at which its
    pseudo-label share of the window's unlabelled pixels is at most **2×** its labelled-GT share (from the 1,912 labelled masks). A class that cannot get under the
    cap below confidence 1 gets no pseudo-labels.
  * The thresholds are **EMA-smoothed with momentum 0.8** (my choice; the spec says only "EMA-smoothed"). They are logged with the raw values in `pseudo_labels.csv`
    and checkpointed with the window histogram.
  * Tests: `tests/test_class_threshold.py` (4 pass: share cap, disabled class, EMA, state round trip, per-class masking). Resume test: PASS (CPU, with the
    checkpoint in the middle of a window).
* **v2 vs `ucf_sl20_stepmatched_s*`: they differ only in the unlabelled loss.** The labelled data (the same 1,912 images), the labelled-image
  augmentation, the model, the optimizer, lr 5e-3 poly and batch 16 are identical. The residual differences that come with having an unlabelled branch at all:
  * the student's forward pass also carries the 8 unlabelled images, so BatchNorm batch statistics mix labelled weak and unlabelled strong crops;
  * the reported model is the EMA teacher rather than the trained network itself;
  * 95,700 vs 95,760 steps (−0.06 %, which shifts the poly schedule negligibly).
* λ = 1.5 with ramp-up, 16 labelled + 8 unlabelled images per step. The unlabelled pool is the other 7,650 train images; their dataset is
  built without masks, so no mask file is ever opened. Total steps are set explicitly: 95,700. SGD lr 5e-3 poly, as in the step-matched SL arm.
* **Choices not stated in Jha et al.** (accepted):
  * **ramp-up shape and length:** the Mean Teacher sigmoid exp(−5(1−t)²) over the first 15,950 steps (5 of the 30 "epochs" of
    the budget; Mean Teacher's ResNet runs ramp over 5 epochs). Jha states λ = 1.5 but no ramp.
  * **SemiCE normalisation:** the masked CE sum divided by *all* unlabelled pixels (FixMatch style), so the term is small while
    few pixels are confident. Jha's Eq. 2 uses 1/N_U with a sum over pixels and a softmax over positions, which cannot be implemented
    as printed.
  * **lr 5e-3 poly** (matched to the step-matched SL arm). Jha states lr 1e-3 for their 30 epochs, with no schedule.
  * **CutMix left out** of the strong view, because it is not photometric (the paired-geometry rule).
  * (Removed: supervised CE on the student's strong view. It was not an accepted choice but a deviation from standard Mean Teacher practice;
    v2 uses the weak view.)
* **Tests** (`tests/test_pvs3.py`, 10 pass: the original 7 unchanged, plus 2 added for v2 and 1 for the pseudo-label logging):
  * hidden masks cannot reach any loss: the step outputs and updated weights are identical whether the unlabelled batch has no mask or masks of 1 or 4,
    and the unlabelled dataset never opens a mask file (patched loader raises);
  * the teacher receives no gradient (no `.grad`, `requires_grad` False), and its new weights equal α·old + (1−α)·student exactly;
  * paired geometry: with the photometric difference removed the two views are bitwise identical over 12 seeds, and with the real strong
    view an asymmetric marker lands on the same pixels in both views;
  * plus checks of the strong-view op list (no geometric ops), the SemiCE threshold and normalisation by hand, and the ramp values;
  * **new, v2:** with `labeled_view: weak` the labelled loss sees the weak view. Changing the labelled strong view leaves the step's outputs
    identical, changing the weak view changes the supervised loss, and with `strong` (v1) the strong view is the one used;
  * **new:** the strong-view probabilities of v1 (1.0 / 0.2 / 1.0) and v2 (0.8 / 0.2 / 0.5), and the op list of the diagnostic transform.
* **Resume test:** **PASS**, bitwise identical, incl. the confident-pixel fraction (CPU, as for UCF supervised). v2: **PASS** (CPU, 22:35 Sat).
* **200-step smoke test (`ucf_pvs3_smoke200`): PASS.**
